# daemon Architecture

`daemon` is the local HTTP/WebSocket server that owns Hiveryn's local state, agent spawn lifecycle, filesystem mutations, and MCP tool surface.

## Purpose

The daemon owns runtime mutations and events. Architects author backlog tickets and project files directly; directory watches reconcile those edits into validation and desktop refreshes. Session transitions and conclusions remain daemon-owned. It owns:

- **Local state**: bootstrap config under `HIVERYN_HOME` (default `~/.hiveryn`) with `config.yaml` plus `variants.yaml`, `architects.yaml`, `tabs.yaml`, and `shortcuts.yaml`; SQLite for sessions, terminal buffers and runtime events.
- **Agent lifecycle**: spawn, kill, and track agent processes through daemon-owned ptys; delegate launch/config synthesis to `agentruntime`.
- **Filesystem mutations**: read/write architect folder markdown (tickets, conclusions, collabs). The architect folder is the shared source of truth; the daemon's SQLite is local-only.
- **MCP tools**: architects use worker spawning, conclusion, questions/notifications, companion messaging/shutdown and read-only readContext/listContext. They author backlog tickets and project context directly through filesystem tools. Workers retain readTicket and concludeTicketSession, read project context with readContext/listContext, but cannot create tickets. Companions get exactly sendMessageToArchitect, replyToArchitectMessage, requestAction and completeCompanionShutdown. Workspace validation is automatic; no inspection/schema MCP tools remain.
- **Built-in instructions**: approved architect SYSTEM/KICKOFF templates are embedded under sessionruntime/prompts/architect; the approved companion SYSTEM (byte-identical to the reviewed draft) and its date-only KICKOFF under prompts/companion. No custom workspace SYSTEM is loaded. Workers receive OVERVIEW.md and explicitly selected plain Markdown workflows in the first message; ordinary resume validates context without reinjection.
- **Event stream**: SSE or WebSocket hints so the desktop app updates views without polling.

**Key rules:**

- `domain/` must not import `store/`, `api/`, or `server/`. It defines the contract everything else depends on.
- `store/` implements repository interfaces from `domain/` where runtime state is persisted in SQLite.
- Config-backed read APIs read from `config/`, not SQLite. Architect/repo lookups plus variant/tab/shortcut reads must come from the current YAML view so edits to `architects.yaml` (and the per-architect `hiveryn.yaml` files it points at), `variants.yaml`, `tabs.yaml`, and `shortcuts.yaml` apply without a daemon restart. `architects.yaml` is a bare `key: path` registry; each architect's name and repos live in its workspace `hiveryn.yaml`, which holds exactly those keys and is decoded strictly (a leftover `prompts:` block or `availableActions` list from the removed Actions feature is a load error). An edit that fails to load never replaces the last valid runtime config: `Source.Current` keeps serving it, logs at ERROR once per distinct error, and `LoadStatus` exposes the failure (`GET /api/system/runtime`); automatic validation and worker launch read `hiveryn.yaml` from disk, so the broken file is reported and blocks new ticket sessions until repaired while architect sessions still start.
- `app/` wires everything together — it's the only package that imports both `store/` and `api/`.
- `sessionruntime/` owns live process/PTY state and bridges `agentruntime` events into persisted session events.
- `sessionruntime/` also owns the in-memory **intent store** (N pending intents per session, keyed by intent id and indexed by session), resolved per-session terminal UUIDs, and right-pane tab layout state for the current run — a single tab list whose terminal tabs are PTY-backed, each keyed by its own UUID in `SessionTab.ID`; SQLite stores durable `sessions`, `session_runs`, and structured events, not terminal identity/layout snapshots or intent state.
- **`Intent` vs `Session`.** A `Session` (table `sessions`) is the durable spawn record — "run an agent for ticket X in workdir Y". An `Intent` is a pending agent tool call awaiting the user's approval. They are unrelated; do not reintroduce `SessionIntent` for either.
- `workspacefs/` is read-only and deterministic: it inspects a workspace and mutates nothing. Missing or invalid files must stay inspectable and repairable rather than block architect startup, so structural problems are reported as diagnostics (`code`/`severity`/`path`/`line`/`message`) and never as failures. Its checks are structural only — no required headings, body schema, line limits or judgments about whether a document's contents are current; `updated_at` is an edit time, reported separately from the filesystem mtime. A file that changes mid-read is reported as `INCOMPLETE_READ` instead of being validated from a torn read. Each artifact kind has exactly one `definition` carrying both its prose (location/naming/rules/example) and its executable field spec: the internal schema description renders it and the check executes it, so the two can never drift. `hiveryn.yaml` is validated through the config loader's own ruleset (`config.ValidateArchitectConfig`) so the check reaches the same verdict the daemon does; repo *paths* are stat'ed by the caller, deliberately outside that ruleset, since a repo directory that moved must not stop the daemon loading the config.
- Workflows are plain Markdown files directly in workflows/. There is no applicability frontmatter, suggestion engine or automatic selection. Canonical selected paths are stored on the session and revalidated at launch/resume; escaping symlinks are refused.
- `logging/` owns append-only JSONL sinks and schema shaping for app logs and request logs. Middleware and services should emit structured fields, not hand-built JSON strings.
- `mcp/` stays transport-focused: role-specific tool registration plus HTTP client shims back into daemon APIs. Keep tool handlers out of `cmd/` and avoid filesystem mutations here.
- `config/` is self-contained. Bootstrap config lives outside SQLite because the server needs it before the DB opens.

## Adding a new resource

Example: adding a SQLite-backed session resource.

1. **Domain** (`internal/domain/session.go`): re-export pure data types from `github.com/hiveryn/shared/domain` (Session/SessionRun/SessionEvent/SessionTab/Intent*/Ticket*/CommitRef/error types/enums/etc.) via type aliases + const re-exports; define `SessionRepository`/`SessionService`/`TicketService` interfaces and any daemon-local contracts (Envelope, AgentStatus, TerminalAttachment, etc.) here. A contract the desktop also parses is not daemon-local — `ArchitectEvent` moved to shared for exactly that reason. The workspace/workflow read contracts (`WorkspaceReport`, `WorkspaceNode`/`WorkspaceEntry`, `WorkspaceDiagnostic`, `ArtifactKind`/`ArtifactSchema`, `Workflow`/`WorkflowList`) live in shared for the same reason: the desktop consumes them alongside the MCP tools. `WorkspaceNode` and `WorkspaceEntry` are deliberately separate types — the report must stay non-recursive or the MCP SDK cannot build an output schema for it, and the workspace genuinely has no grandchildren, since a subdirectory inside `workflows/` is an error rather than something to descend into.
2. **Migration** (`internal/store/migrations/0002_<resource>.sql`): CREATE TABLE. Add to `migrationFiles` slice in `internal/store/migrate.go`.
3. **Repository** (`internal/store/sessions.go`, `internal/store/runs.go`): `SessionStore` methods implementing `domain.SessionRepository` with SQLite queries.
4. **API** (`internal/api/sessions.go`): handlers using `domain.SessionRepository` interface. Use Go 1.24 method-pattern routing (`"POST /api/sessions"`).
5. **Routes** (`internal/api/router.go`): register handler methods in `NewHandler`.
6. **Wiring** (`internal/app/app.go`): instantiate the new store, pass the repo to the handler.

Each resource is self-contained across four packages — no cross-contamination. Handlers don't know SQL. Store doesn't know HTTP.

## Design rules

- Bind to localhost by default. Allow loopback-only addresses in config validation.
- Design for a single local machine: **1 desktop app + 0–2 MCP sessions at a time**. No multi-user concurrency, no connection pooling beyond what stdlib provides. Scale the code for hundreds of APIs and dozens of tables, but the runtime load profile stays a handful of local consumers per machine.
- Use Go 1.24 stdlib `http.ServeMux` method-pattern routing (`"GET /api/agent-profiles/{name}"`). No third-party routers.
- Prefer interfaces over concrete dependencies at handler boundaries.
- One repository file per table/aggregate in `store/`. One handler file per resource in `api/`.
- Migrations are idempotent, versioned, and run inside a transaction per file.
- Access logging, panic recovery, and request IDs are enforced by middleware — not per-handler.
- Structured daemon logs live under `HIVERYN_HOME/logs/daemon.jsonl`; request logs live under `HIVERYN_HOME/logs/requests.jsonl`. Keep every record as single-line valid JSON.
- SQLite uses `SetMaxOpenConns(1)` (single-writer). Busy timeout is 5 seconds.
- Never log secrets from profiles, env configs, or MCP configurations.
- PTY/process handles stay in memory under `sessionruntime`; SQLite stores session metadata and structured events only.
- Every PTY gets the product's own terminal identity, not the daemon launcher's: `mergeProcessEnv` forces `TERM=xterm-256color`/`COLORTERM=truecolor` (what the desktop's `@xterm/xterm` client actually is) and drops the inherited `TMUX`, `TMUX_PANE`, `STY`, `TERM_PROGRAM` and `TERM_PROGRAM_VERSION`. Inheriting them corrupts output — under `TERM=tmux-256color` oh-my-zsh emits titles as `ESC k <title> ESC \`, which xterm.js prints into the buffer instead of consuming. Identity is applied before the caller's `Env`, so a variant profile override still wins. Never log the merged environment; it is the daemon's own, secrets included.
- Architect sessions must not conclude while same-architect ticket sessions are still running, or while any companion the session owns is not settled (`stopped`, `start_failed`, `failed`); return a `Conflict` naming them instead of orphaning PTYs. The companion check also runs before the conclusion approval is shown.
- **Companions** (`sessionruntime/companions*.go`, `actions.go`, `store/companions.go`, migration 0021, shared `companion.go`; contract in `docs/companions.md`). `hiveryn.yaml` `companions: {name: {repo, variant}}`; structural validation in the config ruleset, the variant (claude/codex, the repo's machine) at start. Each new architect session's first live run (`CreateRun`) writes one `companions` record per entry (the session's snapshot, FK-cascaded with it) and launches each in the background through `CreateRun` (session type `companion`, `context_id` = name, `owner_session_id`), then reports every named outcome in one `companion_startup` message to `session:<architect>`. Failed launches are cleaned up with confirmed termination (`start_failed`) or kept visible (`stop_failed`). Messaging is the outbox (`companion_message`/`architect_message`, `session:<id>` recipients, accepted = committed; ownership from the calling session, reply targets from the referenced message). `requestAction` is a question-like single-winner wait (phone alert first, durable `action_request` events, 1 h expiry, cancelled by shutdown request/session end) with decision route `POST /api/sessions/{id}/actions/{actionID}/decision`; it is not an intent, policy or gate engine. Shutdown is the architect's request_id (UUID, bound to both sessions, idempotent per target) and the companion's completion with its handoff; the daemon then confirms termination and reports the outcome; unconfirmed termination stays `stop_failed` until the user's discard confirms it — never forced automatically. `ReconcileCompanions`/`ReconcileActions` run before restore. No listCompanions tool.
- Ticket filesystem mutations are status-gated: only backlog tickets can be edited, metadata-updated, or deleted; backlog or progress tickets can be concluded (worker conclusion still requires progress; architect-driven `move-to-done` accepts either); done tickets are read-only.
- Agent tool calls that need the user's approval route through the **intent system** (`sessionruntime/intents*.go`): the daemon raises a pending intent, publishes a durable `type: "intent"` / `status: "required"` session event carrying `{intent_id, intent_type, summary, payload, origin, wait_seconds, policy}`, and BLOCKS the agent's MCP call on a channel until the user answers or the tool's policy fires. No polling. The side effect lives in the intent's `Exec` and runs only after the intent resolves approved, so enforcement is daemon-side and an agent cannot bypass it. `concludeSession` (every session type) and `spawnTicketWorker` (architects only) are routed today as intents. Backlog authoring uses the filesystem, with no ticket-creation approval or MCP mutation surface. The only agent-initiated spawn is `spawnTicketWorker` (below). The desktop's own direct routes (`POST /api/sessions/{id}/conclude`, `POST /api/architects/{key}/tickets`) stay unapproved because approval gates the agent, not the user.
- **Architect-requested workers** (`sessionruntime/spawn_worker.go`, `POST /api/sessions/{id}/intents/spawn-ticket-worker`). `spawnTicketWorker(ticketId, variant, workflows)` is architect-only (workers never get it) and an intent (`intent_type: spawnTicketWorker`, `wait-then-allow`). Before anything is shown: the ticket's scope machine is derived (`config.ScopeMachine`) and the variant is required and checked against `variants.yaml` for that machine (`requestedVariant`: missing/unknown/other-machine names the target and lists its variants); workflow names resolve through `workspacefs.ResolveWorkflowNames` — `NAME` or `NAME.md` of a file directly in the calling architect's `workflows/`, paths and `.`/`..` refused, equivalents collapsed in first-seen order, unknown names reported with the available ones, and nothing added from repo suggestions (empty selects none); then the full ticket-session contract runs through `ticketSessionParams`, the same resolver `CreateSession` uses (ticket on this architect's board and in backlog, repo scope, `ValidateWorkerContext`). The payload (`ticket_id`, `repo`, `additional_repos`, `variant`, workflow names; title as summary) is the dedup identity; a retry of a request that already launched replays its outcome (`intentStore.Known`) instead of failing the backlog check. On approval or expiry `Exec` re-resolves everything against the live config, board and workspace (variant against the resolved scope machine), creates the session (`created_by: architect`, canonical workflow paths) and launches it through `CreateRun` — so worker-context validation, workflow body delivery and the `session_started` announcement are the desktop's own — and returns `SpawnedTicketWorker` (session, run and main-terminal ids, variant, workflow names and recorded paths) once running, never waiting for the worker. A failed launch resolves `error` with its original cause and deletes the session it created; approval is never reported as a launch. Duplicate workers are prevented by the backlog requirement, intent dedup and the store's one-active-session-per-ticket rule (`CreateSession` and `CreateRun`), which also settles a race with a desktop launch.
- Per-tool policy is a hardcoded table (`intentPolicies` in `sessionruntime/intents_policy.go`) with `auto-allow | wait-then-allow | wait-then-deny`; adding a tool or flipping behavior is a one-line change, and an unregistered tool fails fast rather than defaulting to allow. The wait *window* is shared and comes from config (`intent_wait_timeout`, default 20s); it must stay safely under the smallest agent-runtime tool-call ceiling (~60s) — shrink the window, never raise the ceiling.
- Once an intent is claimed (the user's approval or its policy's expiry) the operation belongs to the daemon: `Exec` runs on `intentExecContext` (detached from the approving request, bounded by `intentExecTimeout`, 3 min — above the 2 min launch and teardown bounds it contains, so they report their own errors), and `Finish` and the resolved event run on `intentFinalizeContext` (detached, 30 s). A claimed intent is announced as `intent`/`resolving` (raw `by: user|policy`); it stays open in the log until `resolved`, approving or denying it again is a `ConflictError` (not 404, which means resolved or foreign), and a restart reconciles it with a reason saying it may have taken effect. A resolved event that cannot be appended because the approved operation removed its own session (a conclusion) is expected and logged at INFO. Ending a session (`ConcludeSession`, `UnspawnTicketSession`, `TerminateSession`) goes through `beginTeardown`: detached, bounded by `sessionTeardownTimeout` (2 min) and one at a time per session (a concurrent end is a `ConflictError`); closing a remote auxiliary terminal is detached and bounded likewise.
- Intents are idempotent within a replay window anchored at resolution — 1h (`intentReplayTTL` in `sessionruntime/intents.go`) — keyed by `hash(session, tool, normalized-args)`. A retry attaches to a live intent or replays the resolved outcome; it never mints a duplicate. An `error` outcome is not replayed: the retry the agent is told is reasonable becomes a fresh request the user approves again (never inherited authorization), and each mutation rechecks its own state when it runs. Consequently an intent does NOT die with the requesting agent's ctx (a tool-call timeout *is* ctx death, and the retry must be able to replay) — a detached owner goroutine holds the timer, and a caller whose ctx dies merely detaches. Anything varying per call (e.g. `CreateTicketParams.Now`) must be stamped inside `Exec`, never in the hashed payload, or dedup silently stops working.
- Intent outcomes are a closed catalog (`approved`, `auto_approved`, `denied_by_user`, `auto_denied`, `error`). A denial is returned to the agent as a SUCCESSFUL tool result carrying the outcome, never as a tool error — a tool error reads to an agent as "bad input, retry", which is the retry loop the catalog exists to prevent. Only `error` is retryable.
- `session_events` keeps a 100-event ring for ordinary session traffic; `type='intent'` and `type='question'` events are excluded from both the count and eviction so pending approval and question state remains replayable throughout its wait window.
- **Agent notifications and questions** (`sessionruntime/questions.go`, `ntfy/`, shared `question.go`). Every session type gets `notify(shortMessage)` and `askQuestion(question, answers, recommendedIndex)`; both return plain text. `notify` (`POST /api/sessions/{id}/notify`) returns exactly `Notification sent to user` only after the ntfy server accepted the alert; missing configuration (`ConflictError`) or a refused/failed publication is an error. `askQuestion` (`POST /api/sessions/{id}/questions`, blocking) publishes the phone alert first — a failed alert fails the call before any question exists — then raises the question as a durable `question`/`required` session event and waits. Exactly one resolution wins under the store's lock: the desktop's answer (`POST /api/sessions/{id}/questions/{qid}/answer`, scoped to the session — another session's question is `NotFound`; a resolved one is a `ConflictError` naming why), the server-side expiry (`domain.QuestionTimeout`, 1h, enforced regardless of the client: provider cancellation is unreliable), the agent's call ending (`cancelled`), the session-end funnel (`cancelled`) or `Shutdown` (`interrupted`). The winner publishes `question`/`resolved` with `status` and `answer` or `reason`. Pending questions live only in memory with their waiter, so an answer is accepted only while the agent's call can still receive it; `ReconcileQuestions` (startup, before restore) resolves any question the log still shows pending as `interrupted`. Bounds, the 0-based required `recommended_index` and the exact reply strings are the shared contract; the recommendation is never applied for the user. Questions are not intents. **Worker question escalation** (`sessionruntime/questions_escalation.go`): a ticket worker's question unanswered by the user for `question_escalation_delay` (config.yaml, default 120 s, 0 disables, must stay under the one-hour expiry) is announced once to its architect through the agent-message outbox (kind `question_escalated`, dedupe `question_escalated:<question_id>`, recipient `architect:<key>`; the body carries ticket, question id, question, choices, recommendation, elapsed seconds, expiry and the agreed "no action is required" wording). The escalation timer lives in the `AskQuestion` select loop and changes nothing about the wait; architect questions never escalate; an enqueue failure is logged and leaves the question pending and unescalated. Architects (only) get `answerQuestion(questionId, answer)` → `POST /api/sessions/{id}/questions/{qid}/architect-answer` → `AnswerQuestionAsArchitect`, authorized from the caller's own session (running architect session of the question's project; the question an escalated ticket-worker question — other projects, unknown ids and non-ticket questions are `NotFound`, a non-architect caller a `ConflictError`). It resolves through the same single-winner `finishQuestion` with `answered_by: architect`; the worker's reply gets `QuestionArchitectAnswerPrefix`, the resolved event `raw.answered_by`. A settled or unescalated question is an `ArchitectAnswerResult` with outcome `not_answerable` (200, never a retryable error). Resolution kicks the dispatcher, whose per-kind `staleChecks` fail a still-pending escalation (`withdrawn: …`) instead of delivering it; a delivered notice for a resolved question is harmless because the answer is refused server-side.
- Every launch and resume sets `StartRequest.DisableNativeQuestions` and gives the `hiveryn-daemon` MCP server `ToolTimeout` 65 min (`hiverynMCPToolTimeout`), beyond the 1h question expiry so the timeout reply arrives. Consequences owned by agentruntime: Claude's MCP auto-backgrounding is off for the whole session; OpenCode's timeout also bounds connecting and listing tools; Codex's model-catalog `request_user_input_async` cannot be disabled. Variant MCP servers keep their provider default.
- **Conversation sends are synchronous** (`sessionruntime/submit.go`). `POST /api/sessions/{id}/messages` records a durable request identity and attempts delivery before answering, bounded by `submitDeliveryBound` (20 s) and detached from the request: 200 only on established provider acceptance (`accepted_at`/`acceptance` evidence, never model completion; Codex native queue counts), otherwise a `domain.DeliveryError` with a stable code (`SESSION_BUSY`, `SEND_UNAVAILABLE`, `DELIVERY_REJECTED`, … definitive and never delivered later; `DELIVERY_UNKNOWN` ambiguous, reconciled from native evidence and never resent) and the receipt in `details.submission`. Hiveryn never queues user input; the same request replays its outcome (a concurrent duplicate waits for the attempt), a definitive refusal is resent only under a new request id. Admission runs under `launchMu` (no network waits there); terminal hand-offs take the per-session hand-off slot shared with the outbox dispatcher (taken → busy; teardown waits for it). Startup `ReconcileSubmissions` turns attempts left `delivering` into rejected (unreserved) or unknown (reserved). Do not reintroduce a deferred user-message queue. The API assumes one connected client: the receipt exists only in that POST's answer (no receipt read/list and no archived-chat discovery endpoint), so a client reconciles by repeating its own request id and follows turns in `GET /conversation`; an ended session keeps its `chat_archives` retention record so its history stays readable by id and new input is `SESSION_ARCHIVED`.
- Interaction mode is independent of role: persisted `terminal` (default, including old rows) or opt-in local `chat`. `sessionruntime/chat.go` owns chat processes, serialized durable submissions and native receipt reconciliation; provider protocol/config belongs in agentruntime's optional `ConversationAdapter`. Chat readiness has a native ID and **no** main terminal UUID; desktop discovers it with a labelled placeholder and normal question/intent event subscriptions. `conversation_submissions` reserves dispatch before handoff; append-only `conversation_items` revisions preserve history and old-item updates; `revision` is the feed cursor, `sequence` the display position, which `PutConversationItems` derives from native record order (late or out-of-order items are placed between their native neighbours as a new revision; never order by timestamp or discovery). The chat owner's internal queue holds only the kickoff and outbox notifications; user input enters only an empty, ready chat (otherwise `SESSION_BUSY`) and is accepted on the transport's `ConversationEvent.Acceptance`. An ambiguous/permission-blocked head holds the chat, never blindly replays. All chat inputs share one submitter. A process-group watchdog observes daemon EOF, and an inherited exclusive lock prevents another owner until the previous one exits. Chat resume requires a specific native ID; never open a picker or attach a second TUI. See `docs/conversation-api.md` for HTTP polling, lifecycle and supported-setting limits.
- **Conversation stream** (`sessionruntime/conversation_stream.go`, `api/conversation_stream.go`). `GET /api/sessions/{id}/stream` is one SSE connection per selected session: `status` and `controls` are authoritative snapshots (re-sent on every connect and change), `conversation` pages are the version feed resumed from `Last-Event-ID` (= the page's `next_revision`), `reset` replays a foreign cursor from 0. Nothing is buffered per client: each subscriber has a one-slot change signal and its handler re-reads the durable sources, so a slow reader lags and catches up, and a blocked write (10 s) drops the connection for a cursor resume. One refcounted observer per watched session reads terminal native records through `syncTerminalHistory` (shared throttle/serialization with `GET /conversation`; remote over the existing per-session master), woken by hook/status events, at least 250 ms (remote 1 s) apart, otherwise every 2 s, backing off to 15 s on failure; reads are detached from subscribers and cancelled only at shutdown, and skipped while a session is ending. It never touches Claude idle evidence, hand-offs or deliveries. Unsupported sessions are refused (422) before streaming; an ended session's stream sends its retained final history, `ended`, and closes. Do not add per-client event queues or a generic event platform.
- **Terminal-session conversations** (`sessionruntime/terminal_conversation.go`). Ordinary laptop (terminal-mode) sessions expose the conversation API without changing ownership: history is read from the provider's own record (agentruntime `HistoryReader`) into the version feed with `via` (terminal/api/notification/kickoff) and unmodified `native_origin`; the recorded launch message is conversation content (`origin`/`via` `kickoff`, verbatim, never reconstructed; chat keeps its native kickoff echo likewise), while role instructions, reasoning and hooks are never read; send uses the provider route the outbox uses (Claude asyncRewake waiter at idle — native `task_notification`, never relabelled human; Codex durable queue with `clientUserMessageId`; OpenCode `prompt_async` at server-reported idle under the latest user turn's agent). Sends are synchronous (above): Claude is accepted only once the input is in its transcript, Codex on `thread/queue/add`, OpenCode on `prompt_async` 2xx; `agentruntime.IsNotDelivered` separates a refusal from an unknown outcome. They reserve provider ref/hand-off time/receiving main terminal before hand-off; the dispatcher only reconciles accepted/unknown input (running/completed/failed/uncertain) from native evidence and never resends (`uncertain` does not hold later terminal input). Claude/OpenCode hand-offs hold laptop keystrokes to the live main terminal (in-memory id, never the SQLite row) for ≤3 s. Never type into the TUI, scrape rendered output or start a second owner. Session end settles from a final native sync (handed → uncertain unless completed). See `docs/conversation-api.md`.
- There are exactly three session types: `architect`, `ticket` and `companion` (daemon-started only; `POST /api/sessions` refuses it). Freeform sessions were removed end to end: `session_type: freeform` is rejected at session creation and by `hiverynd mcp`, migration 0003 deletes any leftover freeform rows, and the historical `freeform/` folders in architect workspaces are user data that the daemon neither reads nor deletes. Do not reintroduce freeform.
- **Actions were removed** (Action registry, definitions, `action` sessions, executeAction/getActionResult tools, artifact packages, attention monitors, `action_ended` messages, the `hiverynd action` CLI and the Actions window). Former Action repositories are ordinary repos used by ticket workers with workflows; there is no execution framework, artifact service or single-run lock replacing them. Migration 0015 drops `action_runs`/`action_artifacts` and retires action sessions, `action_ended` messages and `executeAction` intent records/events; on-disk `action-runs`/`action-artifacts` directories are user data it never touches. Do not reintroduce Actions or a compatibility path.
- **Agent messages** (`sessionruntime/messages*.go`, `store/agent_messages.go`, shared `message.go`, migration 0011). A durable outbox of text the daemon delivers into running agent sessions through each provider's native route (agentruntime `MessageDeliverer` / `ingest.Mailbox`), never by typing into a terminal. Producers call `BeginAgentMessage` (`pending_commit`) before a non-transactional side effect and `CommitAgentMessage` after it, or `EnqueueAgentMessage`; identity is the UNIQUE `dedupe_key` (a retry returns the existing row). Recipients are `architect:<key>` (the running architect session, whichever it is) or `session:<id>`. One dispatcher goroutine (kicked by commits, hook status changes, waiter arming, session end and a 30 s tick) owns every later state change: it resolves the recipient, gates on idle where the provider needs it (Claude: an armed waiter plus the primary agent's last hook event being Stop or a resume/clear SessionStart — a waiter arming or retrying is never idle evidence; with no hook evidence since this daemon process started or since a remote attachment dropped (`forgetMessageActivity`) activity is unknown and only the native record's turn end after the latest input establishes idle, applied only if no hook event changed the gate meanwhile (`sessionruntime/claude_activity.go`); OpenCode: `session.idle`; Codex: never, its queue holds), hands over or pushes one message per target session at a time, confirms the provider's own record before any redelivery (`handed → appeared/acknowledged`, or back to `pending` under the same id when the target went idle again without the message, when the Codex item is neither queued nor recorded, or when the target session ended), backs off failed attempts with a visible `last_error`, and records why an open message is not progressing in `condition`. An absence counts only when the inspected record reaches past the hand-off (`MessageReceipt.RecordedThrough`): a record that ends before it — an old Codex rollout segment, an unflushed file — is stale evidence and the message waits (then falls under the 15-min handed cap). `attempts` counts durably reserved attempts, including unknown acceptance: target identity, provider reference and attempt budget are written before any hand-off, and a failed reservation prevents sending. Transport errors remain `handed` awaiting receipts, subject to the same three-attempt cap. Failed subsequent state writes are retried before further dispatch, retaining confirmed receipts in memory; after restart the durable reservation causes receipt inspection again. OpenCode's `MessagePreparer` chooses a reference before reservation and `DeliverMessage` uses it unchanged. Right before a previously handed message is sent again, the previous target's record is read once more and a receipt closes the message without sending (this is also how open rows are reconciled after a restart or a lookup fix); a record that cannot be read does not block that bounded redelivery. No message ever launches a session: with no running recipient it waits for the next one. Remote Claude and Codex recipients (companions, workers) are delivered over SSH like remote conversation input — Claude to its waiter through a connected attachment, Codex through `codex app-server` on its machine — and confirmed from the mirrored remote record (`readRemoteMessageReceipt`, plus the remote Codex queue); other remote recipients are a retained condition. Architects are always local. Every local launch gets `StartRequest.MessageDelivery` (OpenCode: a daemon-chosen loopback port and password remembered in memory for the process). `pending_commit` rows are reconciled against their producer's side effect at startup (all) and each tick (older than 5 min) through per-kind checks; terminal rows are pruned after 30 days. The first producer is the worker ticket conclusion: `concludeTicketSession` begins the `ticket_concluded` notice ("Ticket <id> has been concluded. Outcome: <outcome>. Read its files in tickets/done/ to review the result.", dedupe `ticket_concluded:<architect>:<ticket>:<concluded_at>`) before `ConcludeTicket` and commits it after; the check promotes it when the ticket is done with that conclusion, fails it as superseded when done with another, as gone when the ticket is missing, and keeps a partial write (conclusion.md present but not moved) visible. A denied conclusion never reaches Exec, and an architect's own moveTicketToDone notifies nobody. The second producer is worker question escalation (above); automatic workspace validation reports are a third (`workspace_validation`). `GET /api/architects/{key}/messages` lists a project's messages; `agent_message_changed` on the architect stream says to list again. Delivery is bounded, not exactly once: the provider crash windows are in each adapter's `MessageCapability.Coverage`, and the idle check and a user submission can still race.
- The only legitimate session ends are the role-scoped conclude tools (`concludeArchitectSession`, `concludeTicketSession`) and explicit ticket-session discard. Discard moves the ticket back to `backlog`, emits an ended session event with `raw.lifecycle=discarded`, kills PTYs, deletes the run, deletes the intent, and writes no conclusion. Any unexpected main agent PTY exit must auto-resume the current run from the stored `native_id` (or id-less resume — a session picker — when `native_id` is empty), publish the new `main_terminal_id`, and leave run status as `running`. A failed resume — on startup restore or after a PTY exit — marks the run failed (`restore_failed` on restore, `launch_failed` on PTY-exit resume), logs at ERROR level, and for ticket sessions moves the ticket back to `backlog`; it never crashes the daemon, and startup continues regardless of individual failures.
- A session becoming live is announced **once**, from `sessionruntime.Service.CreateRun` — the single point where a run has running status and a ready owner (a `main_terminal_id` for terminal mode, structured readiness for chat). It publishes `session_started` on the architect stream carrying `session_id`, plus `ticket_moved` for ticket sessions. Never publish session lifecycle from an HTTP handler: the service is the one place every launch path reaches, and a handler-side publish silently excludes any other caller (this is how MCP-spawned sessions once became invisible to the desktop). `session_ended` is published symmetrically on conclude and discard. This event is the *only* way a client can discover a session it did not create, since subscribing to a session's own stream already requires its id.
- Architect sessions launched with `AgentOpenCode` must define a named `StartRequest.OpenCodeAgentConfig` entry keyed by `architect_key`, use the architect instructions as that agent's `Prompt`, and prepend `--agent <architect_key>` to launch args. Ticket OpenCode sessions must not define a named agent, and architect OpenCode profile args must not include `--agent` because the daemon owns that flag.
- Instructions are additive on every provider and the kickoff stays a separate first message: the Claude adapter is constructed with `AppendInstructions: true` (`--append-system-prompt`, never `--system-prompt`), Codex uses `developer_instructions`, OpenCode an instruction file. The daemon never replaces an agent's native system prompt and never touches repository `AGENTS.md`/`CLAUDE.md`.
- Architect startup remains possible with incomplete project context. Startup and architect-session creation reconcile workspace validation and report all errors through durable messages; the approved kickoff contains project name and session time only.
- Worker launch is gated by workspacefs.ValidateWorkerContext at creation, launch and resume: valid hiveryn.yaml, required OVERVIEW.md with updated_at, and each explicitly selected workflow. Unselected workflows do not block launch. The workspace is not an additional writable directory.
- Workflow selection is explicit and session-owned, including an empty list. The desktop never preselects workflows. Workers receive current Overview and selected Markdown content from validated reads, labelled by name. Active agents are not reinjected after edits.
- `sessions` store the fully resolved create-time contract: `id` (runtime identity), `architect_key`, `session_type`, `context_id` (artifact/context identity), `prompt` (the fixed kickoff, without workflow bodies), primary `workdir`, normalized `additional_repos`, resolved `additional_workdirs`, `workflows` (canonical selected paths), optional `instructions` (built-in role instructions), and lifecycle metadata. Runs copy the repository-scope snapshot. Initial launch, restore, and terminal-exit resume must use stored paths instead of re-resolving mutable ticket or architect repo configuration.
- Tickets require one primary `repo` key and may declare unique, non-overlapping `additional_repos`; every key must exist in the architect's `hiveryn.yaml`. The primary repo selects the kickoff and working directory. Additional repo paths must remain distinct after `filepath.Clean`, and ticket conclusions may reference commits only from the complete ticket scope.
- Ticket `references` are a string list in one strict grammar (shared `domain.ParseReference`): a same-board ticket id, `architect:<relative path>` (the owning architect workspace, on the daemon host) or `<repoKey>:<relative path>` (that configured repo, on its own machine). Absolute, unqualified, URL, traversal and non-canonical values are rejected with remediation — there is no legacy absolute-path reader — and `architect` is a reserved prefix: config refuses it (any case) as a repo key and requires keys to match `domain.ValidRepoKey`. `internal/contextref` resolves a parsed reference against the architect's scope (`Scope`: workspace root plus each repo root with its machine) and inspects/reads it where it lives with symlink containment (`EvalSymlinks` locally, `realpath`/`readlink -f` remotely) — never on the ticket's primary machine and never on another machine as a fallback. `resolved_references` carry `kind`, `status` (`present`/`missing`/`unverified`/`invalid` with `error`), `owner`, `target`, `location` (`local`, `remote` + `machine`, `unknown` — never local), `path_kind` and `access` (the worker tool: `readTicket`/`readContext`/`listContext`). Remote targets keep the batched, detached SSH inspection (bounded at 15 s, shared by concurrent reads, one per machine, only for the tickets returned); a read waits at most 2 s (`remoteWaitBudget`), an unanswered target is `unverified` and its answer is announced as `workspace_changed`/`ticket_updated` (no ticket id); answers and machine failures are reused for 15 s then served stale up to 10 min while refreshed. A malformed entry is a per-reference `INVALID_REFERENCE` warning (with its ticket.md line) and never makes the ticket `INVALID_TICKET`; confirmed absence is `MISSING_REFERENCE`, an uninspectable target `UNVERIFIED_REFERENCE`, an unknown ticket id `BROKEN_REFERENCE`. The workspace check raises `INVALID_REFERENCE` as an error for backlog/progress (so the existing `workspace_validation` message carries it) and a warning for done. API ticket writes reject invalid references. References are read-only context and never enter launch workdir scope or expand writable repo scope. See `docs/context-references.md`.
- **Worker context reads** (`internal/contextref`, `api/context.go`, `mcp/tools_context.go`). Ticket workers get `readContext` and `listContext` (local stdio and the remote gateway alike — both reach `GET /api/sessions/{id}/context/{file,directory}`). Scope is the session record's architect (workspace + configured repos), never request input; an ended (deleted) session reads nothing. Bounded text pages with `sha256`/`size`/`modified_at` identity and `expected_sha256` change detection, non-recursive listings, and a closed `ContextReadStatus` catalog (`unreachable` is never `missing`; symlink escapes are `outside_root`); invalid references are validation errors. Remote reads are one SSH command per call (`remoteReadTimeout` 30 s). Content and the reference query are never logged.
- Conclude tools take discrete structured fields per session type; the daemon renders them into `conclusion.md` (unchanged frontmatter metadata + a canonical markdown body with a fixed per-type section order). This is an input contract rendered in `RequestConclusion` before the approval surface — do not persist a parallel structured copy and do not change the conclusion read structs or frontmatter fields. Every presentational section is a Markdown string authored by the agent, not an array — this deliberately sidesteps the MCP client's required-array-drop bug (a required array field can be silently stripped before it reaches the daemon, yielding a spurious `-32602 missing properties`). `commits` is the sole exception: it is a structured `[]CommitRef` array because it is persisted to frontmatter and read back per-commit, not merely rendered. Required sections are rejected if blank; record "nothing to report" with the literal Markdown `"None"`. Old free-text-body `conclusion.md` files stay readable.
- Ticket-session conclusion commit metadata is stored and returned as structured `{sha, repo}` entries, where `repo` is the architect repo key from config. Legacy conclusion markdown that stored flat SHA arrays must remain readable and resolve those SHAs against the ticket's repo key.
- The architect folder's markdown is the source of truth for tickets and conclusions. `HIVERYN_HOME/config.yaml` is the source of truth for daemon core settings, including the default terminal shell, unless launch flags override it. `HIVERYN_HOME/variants.yaml`, `HIVERYN_HOME/architects.yaml`, `HIVERYN_HOME/tabs.yaml`, and `HIVERYN_HOME/shortcuts.yaml` are the source of truth for variants, the architect registry, tab layouts, and shortcuts when using the default runtime layout; each architect's repo mappings live in the `hiveryn.yaml` at its workspace root. Changes to those YAML files (including the per-architect `hiveryn.yaml`) must be picked up without a daemon restart; SQLite stores runtime state only. `HIVERYN_ENV` identifies the daemon runtime mode but does not change paths by itself.
- All API responses use a standard envelope (`domain.Envelope`) with `data`/`error` (mutually exclusive), `logs`, `commands`, and `meta.request_id`. Handlers write via `writeJSON(w, r, ...)` and `writeError(w, r, ...)` — envelope wrapping is automatic.

## Error handling

- Never swallow error details. Every error path must either return the error verbatim or wrap it with `fmt.Errorf("context: %w", err)`.
- `writeDomainError` must log unexpected errors before converting them to 500 responses.
- All new handlers and service methods must surface internal errors with enough detail to diagnose failures from logs alone.
- Domain errors (Validation, Conflict, NotFound) are the only errors that should be converted to user-facing messages. Everything else is an internal error and must be logged with full context.

## Remote execution

Optional `machines.yaml` maps machine keys to SSH aliases. `hiveryn.yaml` repos accept local string paths or `{path, machine}`; `ArchitectConfig.Repos` holds resolved paths and `RepoMachines` their location. Never stat or home-expand a remote path locally. Scope creation/edits and new worker launches reject stale invalid configuration and cross-machine writable scopes. Local architects remain local and do not receive remote paths as local workdirs.

Variants are machine-scoped (`VariantConfig.Machine`, omitted = local only; an unknown key is a load error). `CreateRun` — reached by every launch — refuses a variant whose machine differs from `session.Machine` (architect sessions are local) through `Config.VariantForMachine`, whose error names the target and the eligible variants; `spawnTicketWorker` checks the same before anything is shown. The run snapshot records the launch machine (`AgentProfileSnapshot.Machine`); remote restore/reattach never consults `variants.yaml`, local resume uses the snapshot and refuses one frozen for another machine, and an older snapshot without the field is never reinterpreted — `session.Machine` stays authoritative.

`remoteexec/` owns safe SSH command/filesystem transport, including the launch-scoped `Connection` (one private OpenSSH master per remote `createRun`, carried on the launch context via `WithConnection`; `Run` uses it only for the same alias while its master is up, otherwise connects directly; closed when the launch returns). Remote launch preparation keeps a fixed command count: one batched repository check, one prerequisite+environment probe, no separate runtime-directory mkdir. Never route anything that outlives the launch (the worker PTY, reconnects, later aux checks) through it, and never log scripts or payloads in its stage timing; `sessionruntime/remote*.go` owns remote worker lifecycle, dedicated authenticated worker HTTP MCP/hook gateways, reverse forwarding and tmux attachment. Provider filesystem preparation remains in agentruntime. A remote SSH PTY exit is a connection event, never permission to resume/spawn a provider. Persist machine/alias/token/port with the session; tokens are excluded from JSON. `remote_resources` records owned auxiliary sockets and private runtime directories for restart/cleanup, not the desktop tab layout. Remote sessions are ticket workers and companions; each gateway serves only its own role's tools (worker tools of its project, or the four companion tools) and companions get no remote-worker instruction suffix. Confirm remote cleanup before writing a local ended lifecycle. Remote restore reattaches the existing process without reinjecting context or re-resolving its machine.

Remote conversations (`sessionruntime/remote_conversation.go`): Claude/Codex history and send for remote terminal workers run over a session-scoped OpenSSH master (lazy, replaced when dead, closed after 2 min idle and at session end) — never the laptop provider home. History mirrors the provider record (agentruntime `RecordLocator`/`HistoryRecordRequester`) incrementally into a private temp dir (appended bytes + 64-byte overlap rewrite check, 8 MiB/command, 512 MiB/session) and reads it with the unchanged readers; Codex input runs `codex app-server` remotely through `CommandFunc` with the frozen env; Claude's waiter reaches the mailbox through the gateway's token path bound to its session, launches add `MessageDelivery` for remote Claude, and shutdown `Interrupt`s remote waiters so they re-arm after restart. Remote OpenCode/chat are `HISTORY_UNSUPPORTED`/`SEND_UNSUPPORTED`; history failures are `domain.ConversationError` (`HISTORY_*`). A remote reconnect is never a provider restart (`processReplaced`).

Git commands use the configured SSH location. See `docs/remote-workers.md` and the disposable `scripts/remote-smoke.py` for setup and verification boundaries.

## Filesystem authoring and protection

Architects author backlog tickets directly; title, repo, created_at and updated_at are required, while identity/status come from the folder. Workers have no ticket-creation tool. Directory watches in workspacewatch group edits after two seconds of quiet and publish refresh hints plus complete error messages. Reconcile at startup and architect-session creation. Do not suppress previously reported diagnostics in a later message.

architectfs.Protection persists accepted fingerprints through domain.WorkspaceRecords/store.WorkspaceRecordStore. External changes to progress/done records and all conclusions are visible conflicts, never automatic lifecycle transitions or automatic reverts. Daemon-owned mutations serialize with reconciliation and update only their affected records. Invalid ticket rows remain visible. Never infer an active worker's scope from externally edited files.

Imported completed tickets retain missing or retired historical repository scope with warnings; do not invent ownership. Backlog, progress and newly created records require valid configured scope.
