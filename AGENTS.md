# daemon Architecture

`daemon` is the local HTTP/WebSocket server that owns Hiveryn's local state, agent spawn lifecycle, filesystem mutations, and MCP tool surface.

## Purpose

The daemon is the **single mutation and event hub** for Hiveryn. Every state change — whether initiated by the desktop app, an MCP tool call from a running agent, or a lifecycle event from `agentruntime` — flows through the daemon. It owns:

- **Local state**: bootstrap config under `HIVERYN_HOME` (default `~/.hiveryn`) with `config.yaml` plus `variants.yaml`, `architects.yaml`, `tabs.yaml`, and `shortcuts.yaml`; SQLite for sessions, terminal buffers, runtime events and deferred-intent outcomes.
- **Agent lifecycle**: spawn, kill, and track agent processes through daemon-owned ptys; delegate launch/config synthesis to `agentruntime`.
- **Filesystem mutations**: read/write architect folder markdown (tickets, conclusions, collabs). The architect folder is the shared source of truth; the daemon's SQLite is local-only.
- **MCP tools**: exposed by the daemon so running agents can mutate ticket state (create tickets, conclude sessions) without direct filesystem access, plus the read-only architect workspace tools `checkWorkspace` and `describeArtifact`. The architect edits `hiveryn.yaml`, the project documents and workflows with its own file tools; there is no config-authoring, prompt or spawn tool. Only the user launches workers, from the desktop.
- **Built-in instructions**: architect and worker role instructions and kickoffs are embedded markdown in the daemon (`sessionruntime/prompts/{architect,work}/{SYSTEM,KICKOFF}.md`; kickoff placeholders are daemon-supplied values only), and nothing in `hiveryn.yaml` points at a prompt file. The optional `ARCHITECT_SYSTEM.md` in the workspace is appended to the architect instructions; workers read `PROJECT_OVERVIEW.md`, `PROJECT_STATE.md`, the optional `ROADMAP_CURRENT.md` and their explicitly selected `workflows/*.md` live from the architect workspace.
- **Event stream**: SSE or WebSocket hints so the desktop app updates views without polling.

**Key rules:**

- `domain/` must not import `store/`, `api/`, or `server/`. It defines the contract everything else depends on.
- `store/` implements repository interfaces from `domain/` where runtime state is persisted in SQLite.
- Config-backed read APIs read from `config/`, not SQLite. Architect/repo lookups plus variant/tab/shortcut reads must come from the current YAML view so edits to `architects.yaml` (and the per-architect `hiveryn.yaml` files it points at), `variants.yaml`, `tabs.yaml`, and `shortcuts.yaml` apply without a daemon restart. `architects.yaml` is a bare `key: path` registry; each architect's name, repos and optional `availableActions` live in its workspace `hiveryn.yaml`, which holds exactly those keys and is decoded strictly (a leftover `prompts:` block is a load error). An edit that fails to load never replaces the last valid runtime config: `Source.Current` keeps serving it, logs at ERROR once per distinct error, and `LoadStatus` exposes the failure (`GET /api/system/runtime`); `checkWorkspace` and worker launch read `hiveryn.yaml` from disk, so the broken file is reported and blocks new ticket sessions until repaired while architect sessions still start.
- `app/` wires everything together — it's the only package that imports both `store/` and `api/`.
- `sessionruntime/` owns live process/PTY state and bridges `agentruntime` events into persisted session events.
- `sessionruntime/` also owns the in-memory **intent store** (N pending intents per session, keyed by intent id and indexed by session), resolved per-session terminal UUIDs, and right-pane tab layout state for the current run — a single tab list whose terminal tabs are PTY-backed, each keyed by its own UUID in `SessionTab.ID`; SQLite stores durable `sessions`, `session_runs`, and structured events, not terminal identity/layout snapshots or intent state.
- **`Intent` vs `Session`.** A `Session` (table `sessions`) is the durable spawn record — "run an agent for ticket X in workdir Y". An `Intent` is a pending agent tool call awaiting the user's approval. They are unrelated; do not reintroduce `SessionIntent` for either.
- `workspacefs/` is read-only and deterministic: it inspects a workspace and mutates nothing. Missing or invalid files must stay inspectable and repairable rather than block architect startup, so structural problems are reported as diagnostics (`code`/`severity`/`path`/`line`/`message`) and never as failures. Its checks are structural only — no required headings, body schema, line limits or judgments about whether a document's contents are current; `lastUpdatedAt` is an edit time, reported separately from the filesystem mtime. A file that changes mid-read is reported as `INCOMPLETE_READ` instead of being validated from a torn read. Each artifact kind has exactly one `definition` carrying both its prose (location/naming/rules/example) and its executable field spec: `describeArtifact` renders it and the check executes it, so the two can never drift. `hiveryn.yaml` is validated through the config loader's own ruleset (`config.ValidateArchitectConfig`) so the check reaches the same verdict the daemon does; repo *paths* are stat'ed by the caller, deliberately outside that ruleset, since a repo directory that moved must not stop the daemon loading the config.
- Workflows are flat `workflows/*.md` with `attach: manual` or `attach: suggested` + a nonempty list of configured repo keys. There are no dependencies (enforced structurally: the frontmatter is exclusive), no always-attached category and no precedence engine — a repo match is a suggestion, never an obligation, and contradictions between workflow bodies are an agent/user decision. Suggestions match **any** repo in the writable scope; an empty scope suggests nothing, and an invalid workflow is reported with its diagnostics and excluded from suggestions rather than silently dropped. Selection records canonical in-workspace paths: workflows are never copied or snapshotted, and a symlink resolving outside the workspace is refused, not followed.
- `logging/` owns append-only JSONL sinks and schema shaping for app logs and request logs. Middleware and services should emit structured fields, not hand-built JSON strings.
- `mcp/` stays transport-focused: role-specific tool registration plus HTTP client shims back into daemon APIs. Keep tool handlers out of `cmd/` and avoid filesystem mutations here.
- `config/` is self-contained. Bootstrap config lives outside SQLite because the server needs it before the DB opens.

## Adding a new resource

Example: adding a SQLite-backed session resource.

1. **Domain** (`internal/domain/session.go`): re-export pure data types from `github.com/hiveryn/shared/domain` (Session/SessionRun/SessionEvent/SessionTab/Intent*/Ticket*/CommitRef/error types/enums/etc.) via type aliases + const re-exports; define `SessionRepository`/`SessionService`/`TicketService` interfaces and any daemon-local contracts (Envelope, AgentStatus, TerminalAttachment, etc.) here. A contract the desktop also parses is not daemon-local — `ArchitectEvent` moved to shared for exactly that reason. The workspace/workflow read contracts (`WorkspaceReport`, `WorkspaceNode`/`WorkspaceEntry`, `WorkspaceDiagnostic`, `ArtifactKind`/`ArtifactSchema`, `Workflow`/`WorkflowList`) live in shared for the same reason: the desktop consumes them alongside the MCP tools. `WorkspaceNode` and `WorkspaceEntry` are deliberately separate types — the report must stay non-recursive or the MCP SDK cannot build an output schema for it, and the workspace genuinely has no grandchildren, since a subdirectory inside `workflows/` is an error rather than something to descend into.
2. **Migration** (`internal/store/migrations/0002_<resource>.sql`): CREATE TABLE. Add to `migrationFiles` slice in `internal/store/migrate.go`.
3. **Repository** (`internal/store/sessions.go`, `internal/store/runs.go`): `SessionStore` methods implementing `domain.SessionRepository` with SQLite queries.
4. **API** (`internal/api/sessions.go`): handlers using `domain.SessionRepository` interface. Use Go 1.24 method-pattern routing (`"POST /api/sessions"`).
5. **Routes** (`internal/api/router.go`): register handler methods in `NewHandler`.
6. **Wiring** (`internal/app/app.go`): instantiate the new store, pass the repo to the handler.

Each resource is self-contained across four packages — no cross-contamination. Handlers don't know SQL. Store doesn't know HTTP.

## Design rules

- Bind to localhost by default. Allow loopback-only addresses in config validation.
- Design for a single local machine: **1 desktop app + 0–2 MCP sessions at a time**. No multi-user concurrency, no connection pooling beyond what stdlib provides. Scale the code for hundreds of APIs and dozens of tables, but the runtime load profile stays a handful of local consumers per machine.
- Use Go 1.24 stdlib `http.ServeMux` method-pattern routing (`"GET /api/agent-profiles/{name}"`). No third-party routers.
- Prefer interfaces over concrete dependencies at handler boundaries.
- One repository file per table/aggregate in `store/`. One handler file per resource in `api/`.
- Migrations are idempotent, versioned, and run inside a transaction per file.
- Access logging, panic recovery, and request IDs are enforced by middleware — not per-handler.
- Structured daemon logs live under `HIVERYN_HOME/logs/daemon.jsonl`; request logs live under `HIVERYN_HOME/logs/requests.jsonl`. Keep every record as single-line valid JSON.
- SQLite uses `SetMaxOpenConns(1)` (single-writer). Busy timeout is 5 seconds.
- Never log secrets from profiles, env configs, or MCP configurations.
- PTY/process handles stay in memory under `sessionruntime`; SQLite stores session metadata and structured events only.
- Every PTY gets the product's own terminal identity, not the daemon launcher's: `mergeProcessEnv` forces `TERM=xterm-256color`/`COLORTERM=truecolor` (what the desktop's `@xterm/xterm` client actually is) and drops the inherited `TMUX`, `TMUX_PANE`, `STY`, `TERM_PROGRAM` and `TERM_PROGRAM_VERSION`. Inheriting them corrupts output — under `TERM=tmux-256color` oh-my-zsh emits titles as `ESC k <title> ESC \`, which xterm.js prints into the buffer instead of consuming. Identity is applied before the caller's `Env`, so a variant profile override still wins. Never log the merged environment; it is the daemon's own, secrets included.
- Architect sessions must not conclude while same-architect ticket sessions are still running; return a `Conflict` with the active ticket session IDs instead of orphaning PTYs.
- Ticket filesystem mutations are status-gated: only backlog tickets can be edited, metadata-updated, or deleted; backlog or progress tickets can be concluded (worker conclusion still requires progress; architect-driven `move-to-done` accepts either); done tickets are read-only.
- Agent tool calls that need the user's approval route through the **intent system** (`sessionruntime/intents*.go`): the daemon raises a pending intent, publishes a durable `type: "intent"` / `status: "required"` session event carrying `{intent_id, intent_type, summary, payload, origin, wait_seconds, policy}`, and — for a blocking tool — BLOCKS the agent's MCP call on a channel until the user answers or the tool's policy fires (a deferred tool returns immediately; see below). No polling. The side effect lives in the intent's `Exec` and runs only after the intent resolves approved, so enforcement is daemon-side and an agent cannot bypass it. `concludeSession` and `createWorkTicket` are routed today as blocking intents, and the architect's `executeAction` as a deferred one. Other mutating tools (ticket edits) write directly — they are architect-owned bookkeeping guarded by validation, with prompt-level guidance to discuss material changes; routing one later is a one-line `intentPolicies` addition. There is no agent-initiated spawn: only the user launches workers, from the desktop. The desktop's own direct routes (`POST /api/sessions/{id}/conclude`, `POST /api/architects/{key}/tickets`) stay unapproved because approval gates the agent, not the user.
- An intent may carry an **approval-input schema** (`intentSpec.Inputs`, a bounded list of `IntentInputField`: `text`, `textarea`, `choice` from supplied options, `boolean`, each optionally required with an optional typed default). An input-bearing intent is always **deferred** (below): `awaitIntent` refuses a spec with inputs, so no agent call ever blocks on a form and no timer ever approves one. The schema is checked structurally before any popup (a malformed one is a programmer error), rides on the `intent/required` event as `raw.inputs`, and is part of the dedup key; submitted values are not. Defaults only prefill the desktop form: the daemon never applies them, never substitutes them for a missing value, and does not validate them up front. `Exec` receives exactly the user's submitted values validated by `resolveIntentInputs` (`sessionruntime/intents_inputs.go`, `POST …/approve` with optional `{"inputs": {...}}`). Validation runs before the claim, so invalid or missing input is a 400 `ValidationError` that leaves the intent pending, unclaimed and correctable. Denial takes no inputs. Approved values are returned in `IntentResolution.Inputs`/`DeferredIntent.inputs` and recorded as `raw.inputs` on the resolved event.
- **Deferred intents** (policy `manual`, `sessionruntime/intents_deferred.go`) are requested through `submitDeferredIntent`, which returns at once with the stable intent id and a `DeferredIntent` in status `pending_approval`; only the user resolves one — there is no wait window, `wait_seconds` is 0 and the desktop shows no countdown. Each also has a durable SQLite record (`deferred_intents`, no FK to `sessions` so it outlives its session) with the lifecycle `pending_approval → running → completed | failed`, or `→ denied` (reason kept), or `→ failed` without `approved_at` when its session ends or the daemon restarts first. Approval (`running`, `approved_at`) is recorded before the operation starts and its outcome after, so acceptance and success are never conflated; the operation runs detached from the approving request's ctx. The in-memory intent keeps session scoping, the single-winner claim and retry dedup (a retry returns the same id, pending or resolved within its replay window); record writes are compare-and-set on status, and a denial or approval that cannot be recorded releases the claim instead of executing. A restart cannot resume a captured `Exec`: `ReconcileIntents` fails every open record (pending as never run, running as interrupted — may or may not have taken effect) before the listener starts, and its resolved event carries `raw.status: failed`. Resolved records are retained 30 days and pruned at startup and on submission. `GET /api/sessions/{id}/intents/{intentID}` (`SessionService.GetDeferredIntent`) returns the record by id, scoped to the origin session (another session's id is a 404); a tool whose own record is authoritative for the outcome keeps it in step through `intentSpec.Hooks` (`deferredHooks`: `Created`, `Denied`, `Abandoned`). `executeAction` is the one production deferred tool; tests also register fixture types.
- Per-tool policy is a hardcoded table (`intentPolicies` in `sessionruntime/intents_policy.go`) with the blocking `auto-allow | wait-then-allow | wait-then-deny` and the deferred `manual`; adding a tool or flipping behavior is a one-line change, and an unregistered tool fails fast rather than defaulting to allow. The wait *window* is shared and comes from config (`intent_wait_timeout`, default 20s); it must stay safely under the smallest agent-runtime tool-call ceiling (~60s) — shrink the window, never raise the ceiling.
- Intents are idempotent within a replay window anchored at resolution — 1h by default, 10 min for `executeAction` (`intentReplayTTLs` in `sessionruntime/intents.go`) — keyed by `hash(session, tool, normalized-args)`. A retry attaches to a live intent or replays the resolved outcome; it never mints a duplicate. Consequently an intent does NOT die with the requesting agent's ctx (a tool-call timeout *is* ctx death, and the retry must be able to replay) — a detached owner goroutine holds the timer, and a caller whose ctx dies merely detaches. Anything varying per call (e.g. `CreateTicketParams.Now`) must be stamped inside `Exec`, never in the hashed payload, or dedup silently stops working.
- Intent outcomes are a closed catalog (`approved`, `auto_approved`, `denied_by_user`, `auto_denied`, `error`). A denial is returned to the agent as a SUCCESSFUL tool result carrying the outcome, never as a tool error — a tool error reads to an agent as "bad input, retry", which is the retry loop the catalog exists to prevent. Only `error` is retryable.
- `session_events` keeps a 100-event ring for ordinary session traffic; `type='intent'` events are excluded from both the count and eviction so pending approval state remains replayable throughout its wait window.
- There are exactly three session types: `architect`, `ticket` and `action`. Freeform sessions were removed end to end: `session_type: freeform` is rejected at session creation and by `hiverynd mcp`, migration 0003 deletes any leftover freeform rows, and the historical `freeform/` folders in architect workspaces are user data that the daemon neither reads nor deletes. Do not reintroduce freeform. `action` sessions are created only by `LaunchAction` (`POST /api/sessions` rejects them) and belong to no architect: `architect_key` is empty and `context_id` is the execution id.
- **Actions** (`sessionruntime/actions*.go`, `actionfs/`, `store/action_runs.go`). An Action is a Git repository at `HIVERYN_HOME/actions/<name>` (the directory name is the action name) defined by `action.yaml` — exactly `name` (== directory name), `description` (what the prompt must contain) and `artifacts` (the delivered package contract), decoded strictly — and `KICKOFF.md`, which must contain `{{prompt}}` and `{{output_dir}}` and no other `{{…}}` placeholder. Definitions are read live; an invalid one is listed with its problems and refuses to launch. A manual launch (`POST /api/actions/{name}/runs`, prompt + variant) is the user's approval, so no intent is raised: it inserts the `action_runs` record as `running` (a partial unique index makes each action single-run globally — a busy launch is a 409 naming the running execution), creates the empty output directory `HIVERYN_HOME/action-runs/<name>/<execution id>` outside the repo, and starts an `action` session with the repo as workdir and the output directory as its only additional (writable) workdir, the built-in `prompts/action/{SYSTEM,KICKOFF}.md` instructions and the rendered KICKOFF.md. The execution id is the stable caller-visible identity; the output path is structured run data. The record stays `running` after launch and ends only through the agent's `concludeSession` (`completed` — refused while the output directory is empty — or `failed`, with a summary ≤ 2000 chars), the user's cancel (`POST /api/action-runs/{id}/cancel`, failed "cancelled by user"), or a launch/resume/restore failure (failed with the reason; the session is removed). Findings inside a delivered package are still `completed`. Restart: running action sessions are restored like every session and keep their execution running; `ReconcileActionRuns` then fails any execution left running without a live session. Execution history is never pruned (unlike deferred intents). Action agents get only `readRecentConclusions` (latest five summaries of their action) and `concludeSession`; their MCP server has no architect key. `GET /api/actions/events` streams `action_changed` on every request/start/end (no backlog).
- **Architect-requested Actions** (`sessionruntime/actions_architect.go`). An architect sees only the Actions its `hiveryn.yaml` lists under `availableActions` (omitted = none; a listed name without a valid definition is reported invalid by `getAvailableActions`, never dropped, and is not a config load error). `executeAction` is a deferred intent (`intent_type: executeAction`, policy `manual`) with one required `variant` choice and no default; the intent id is the execution id. Its `deferredHooks` keep the `action_runs` record in step: `Created` inserts it `pending_approval` (trigger `architect`, `architect_key`, `requester_session_id`), `Denied` makes it `denied` with the reason, `Abandoned` (requesting session ended, or the request could not be shown) fails it as never run, and `ReconcileActionRuns` fails pending requests at startup. Approval rechecks availability, variant, definition and — under `launchMu` via `StartActionRun`'s compare-and-set — the single-run rule, then launches through the same `launchActionSession` as a manual run; any failure before launch fails the request "could not start". After launch the Action lifecycle is authoritative: the generic deferred record completing (and its 30-day pruning) never touches the execution, and results are read only from `action_runs`, scoped to the architect key (not the session), so later sessions of the same architect keep access and other architects get `NOT_FOUND`. `waitForActionResult` subscribes to the action event hub before its first read (no missed transitions), returns on a status change or at once when final, and is capped at 30 s; its end never affects the execution. Action agents get no Actions tools.
- The only legitimate session ends are the role-scoped conclude tools (`concludeArchitectSession`, `concludeTicketSession`) and explicit ticket-session discard. Discard moves the ticket back to `backlog`, emits an ended session event with `raw.lifecycle=discarded`, kills PTYs, deletes the run, deletes the intent, and writes no conclusion. Any unexpected main agent PTY exit must auto-resume the current run from the stored `native_id` (or id-less resume — a session picker — when `native_id` is empty), publish the new `main_terminal_id`, and leave run status as `running`. A failed resume — on startup restore or after a PTY exit — marks the run failed (`restore_failed` on restore, `launch_failed` on PTY-exit resume), logs at ERROR level, and for ticket sessions moves the ticket back to `backlog`; it never crashes the daemon, and startup continues regardless of individual failures.
- A session becoming live is announced **once**, from `sessionruntime.Service.CreateRun` — the single point where a run has both a running status and a `main_terminal_id`. It publishes `session_started` on the architect stream carrying `session_id`, plus `ticket_moved` for ticket sessions. Never publish session lifecycle from an HTTP handler: the service is the one place every launch path reaches, and a handler-side publish silently excludes any other caller (this is how MCP-spawned sessions once became invisible to the desktop). `session_ended` is published symmetrically on conclude and discard. This event is the *only* way a client can discover a session it did not create, since subscribing to a session's own stream already requires its id.
- Architect sessions launched with `AgentOpenCode` must define a named `StartRequest.OpenCodeAgentConfig` entry keyed by `architect_key`, use the architect instructions as that agent's `Prompt`, and prepend `--agent <architect_key>` to launch args. Ticket OpenCode sessions must not define a named agent, and architect OpenCode profile args must not include `--agent` because the daemon owns that flag.
- Instructions are additive on every provider and the kickoff stays a separate first message: the Claude adapter is constructed with `AppendInstructions: true` (`--append-system-prompt`, never `--system-prompt`), Codex uses `developer_instructions`, OpenCode an instruction file. The daemon never replaces an agent's native system prompt and never touches repository `AGENTS.md`/`CLAUDE.md`.
- Architect startup must stay possible in an incomplete workspace so it can be repaired: the fixed kickoff (project, session start, repos) opens with `Start by running checkWorkspace.`, and a present-but-unloadable `ARCHITECT_SYSTEM.md` is surfaced inside the instructions (with its diagnostics) and logged at ERROR, never silently treated as loaded.
- Worker launch is gated by `workspacefs.ValidateWorkerContext`, rerun against the live workspace at session creation, `CreateRun`, restore and main-terminal resume: `hiveryn.yaml` must load, `PROJECT_OVERVIEW.md` and `PROJECT_STATE.md` must be valid, `ROADMAP_CURRENT.md` is optional but must be valid when present, and every selected workflow must be a unique canonical path to a valid file directly inside `workflows/`. Failures are `*domain.ValidationError` (`field: workspace` or `workflows`) listing every finding; a missing, renamed, invalid or non-canonical selected file fails the launch and is never dropped or substituted. Unselected invalid workflows and `ARCHITECT_SYSTEM.md` never block a worker. A client that needs to show launch blockers before creating a session asks `GET /api/architects/{key}/workspace/worker-preflight`, which runs that same project-context validation — never `checkWorkspace.valid`, which is a wider verdict and would refuse launches the daemon accepts. The workspace is read-only context for the worker — never add it to `AdditionalWorkdirs`, whose meaning is a write grant.
- Workflow selection is explicit and session-owned: `CreateSessionRequest.Workflows` (ticket sessions only; empty is valid) is persisted as `sessions.workflows` and retained across runs and resumes. Repository matches are suggestions computed by `ListWorkflows` for the desktop to preselect; the daemon never attaches a workflow on its own, infers dependencies, copies or snapshots files, or embeds workflow bodies in a prompt. There are no content digests: an active agent is not updated by a file edit, and on resume `resumeInstructions` tells it to reread the selected canonical paths rather than claiming they are unchanged.
- `sessions` store the fully resolved create-time contract: `id` (runtime identity), `architect_key`, `session_type`, `context_id` (artifact/context identity), `prompt` (the fixed kickoff), primary `workdir`, normalized `additional_repos`, resolved `additional_workdirs`, `workflows` (canonical selected paths), optional `instructions` (built-in role instructions), and lifecycle metadata. Runs copy the repository-scope snapshot. Initial launch, restore, and terminal-exit resume must use stored paths instead of re-resolving mutable ticket or architect repo configuration.
- Tickets require one primary `repo` key and may declare unique, non-overlapping `additional_repos`; every key must exist in the architect's `hiveryn.yaml`. The primary repo selects the kickoff and working directory. Additional repo paths must remain distinct after `filepath.Clean`, and ticket conclusions may reference commits only from the complete ticket scope.
- Ticket `references` remain a portable string list and may contain same-board ticket IDs or normalized absolute filesystem paths. API ticket views expose daemon-resolved reference type, existence, and file/directory kind. External path references are contextual pointers carried in kickoff guidance and never enter launch workdir scope or expand writable repo scope.
- Conclude tools take discrete structured fields per session type; the daemon renders them into `conclusion.md` (unchanged frontmatter metadata + a canonical markdown body with a fixed per-type section order). This is an input contract rendered in `RequestConclusion` before the approval surface — do not persist a parallel structured copy and do not change the conclusion read structs or frontmatter fields. Every presentational section is a Markdown string authored by the agent, not an array — this deliberately sidesteps the MCP client's required-array-drop bug (a required array field can be silently stripped before it reaches the daemon, yielding a spurious `-32602 missing properties`). `commits` is the sole exception: it is a structured `[]CommitRef` array because it is persisted to frontmatter and read back per-commit, not merely rendered. Required sections are rejected if blank; record "nothing to report" with the literal Markdown `"None"`. Old free-text-body `conclusion.md` files stay readable.
- Ticket-session conclusion commit metadata is stored and returned as structured `{sha, repo}` entries, where `repo` is the architect repo key from config. Legacy conclusion markdown that stored flat SHA arrays must remain readable and resolve those SHAs against the ticket's repo key.
- The architect folder's markdown is the source of truth for tickets and conclusions. `HIVERYN_HOME/config.yaml` is the source of truth for daemon core settings, including the default terminal shell, unless launch flags override it. `HIVERYN_HOME/variants.yaml`, `HIVERYN_HOME/architects.yaml`, `HIVERYN_HOME/tabs.yaml`, and `HIVERYN_HOME/shortcuts.yaml` are the source of truth for variants, the architect registry, tab layouts, and shortcuts when using the default runtime layout; each architect's repo mappings live in the `hiveryn.yaml` at its workspace root. Changes to those YAML files (including the per-architect `hiveryn.yaml`) must be picked up without a daemon restart; SQLite stores runtime state only. `HIVERYN_ENV` identifies the daemon runtime mode but does not change paths by itself.
- All API responses use a standard envelope (`domain.Envelope`) with `data`/`error` (mutually exclusive), `logs`, `commands`, and `meta.request_id`. Handlers write via `writeJSON(w, r, ...)` and `writeError(w, r, ...)` — envelope wrapping is automatic.

## Error handling

- Never swallow error details. Every error path must either return the error verbatim or wrap it with `fmt.Errorf("context: %w", err)`.
- `writeDomainError` must log unexpected errors before converting them to 500 responses.
- All new handlers and service methods must surface internal errors with enough detail to diagnose failures from logs alone.
- Domain errors (Validation, Conflict, NotFound) are the only errors that should be converted to user-facing messages. Everything else is an internal error and must be logged with full context.

## Development

- `make vet` — static analysis
- `make test` — run all tests
- `make build` — compile check all packages
- `make lint` — golangci-lint (v2 config, same linter set as `agentruntime`)
- Run `make tidy && git diff --exit-code -- go.mod go.sum` before merging.
